## 1. 项目现状

这是一个 Godot 4.7.2 的 3D 六边形塔防项目：

- `sim/` 负责确定性模拟，有 16 个黄金指纹保护回放结果。
- `game/app/` 负责主循环、对局生命周期和输入分发。
- `game/view/` 负责地形、模型、相机、音效和每帧画面同步。
- `game/ui/` 负责 HUD、页面、开屏和隐私门。
- `tests/` 当前单测汇总为 134 例；另有黄金、场景、输入、截图等探针。

项目已有不少有效优化，不能重复做或误报：场外地形采样已多线程，模型资源有缓存，远距离模型有分级细节，菜单有限帧，UI 有统一风格与守规检查。

## 3. 最严重的五个问题

### P0-1 工人链路有两处真实运行错误，测试还会误报通过

**收益：极高；修改成本：低；必须先修。**

已确认两个独立问题：

1. 无矿可采时，模拟层仍可能用 `target=-1` 去取矿格。
   - 位置：`sim/world.gd:776-788`
   - 触发方式：第一次找不到矿后会原地等待；下一 tick 若地图版本没变，就跳过重新挑选，却没有再次拦截 `target < 0`，随后访问 `ore_cells[-1]`。
   - 本次单测因此产生 5062 条越界错误。

2. 工人第一次出现在画面时，视图层把不存在的字典项当成固定 `Dictionary`。
   - 位置：`game/view/view_entities.gd:1185-1199`
   - `worker_nodes.get(wid)` 在首次出现时是空值，赋给 `var e: Dictionary` 会直接报运行错误，后续每帧重复。
   - 场景探针虽打印 PASS，实际上工人画面同步已经报错。

同时，`tests/kit.gd:58-72` 只统计断言失败，不知道 Godot 已打印 `SCRIPT ERROR`，所以会给出“0 失败”的假绿结论。

**建议改法：**分三个小步，不混成一块改：先修模拟层空目标并补连续多 tick 无矿测试；再修视图层首次工人同步并补探针；最后给测试命令加错误日志拦截，出现 `SCRIPT ERROR` 就判失败。这样能防止同类问题再次假装通过。

### P1-2 改一格地形，仍会重算整张地图

**收益：高；修改成本：中。**

证据链：

- `game/view/view_entities.gd:610-612` 发现高度变化就调用 `_rebuild_field()`。
- `game/view/view_terrain.gd:1319-1322` 直接进入 `_rebuild_hex()`。
- `game/view/view_terrain.gd:829-1056` 会重新计算全部 4096 格、重新生成顶点与索引、重新上传网格，并重建岩石和草道具。

这意味着一次局部挖填也要支付整张地图的费用，容易造成操作瞬间卡顿；若以后扩到 128×128，工作量还会进一步扩大。

**建议改法：**先在当前 64×64 版本实测单次重建耗时，再做“改动格及邻居”的局部更新，保留开图时的全量构建入口和公开函数签名。异步只减少主线程等待，不会减少总计算量，不能与局部更新混为一谈。此项应与现有 CAMERA-MAP 计划中的地形性能任务合并，避免做两套方案。

### P1-3 每帧实体同步存在明显的重复计算

**收益：中高；修改成本：中。**

主要在 `game/view/view_entities.gd`：

- `1044-1114`：每只虫都会再遍历所有虫，计算彼此距离。虫数为 N 时，每帧比较约 N×N 次；同时还要排序、建分组字典。
- `651-676`：每帧重新创建建筑、墙体和变更字典，并遍历建筑；`678-788` 又继续遍历和更新大量静态信息。
- 这些临时字典每帧重新出现，会增加内存分配和清理压力。

建筑位置查询本身已有 `by_cell` 缓存，不是线性查找，这一点不再误报为问题。

**建议改法：**虫群只比较同格和邻近格，静态建筑只在新增、删除、施工或地形变化时刷新，临时容器尽量复用。保持 `sync(world, tick_alpha, delta)` 的签名与画面顺序不变，用现有同步探针和实际大波次帧时间验收。

### P2-4 模型第一次使用时才加载，每个实例还重复做相同校准

**收益：中；修改成本：低到中，需计时确认。**

- `game/view/models.gd:135-141` 已缓存加载后的场景，这是正确基础。
- 但 `204-218` 的单位首次生成仍会触发加载，每个实例还会重新遍历模型计算包围盒、查找动画和分级节点。
- 建筑在 `286-307` 也有相同的逐实例校准。

风险主要在某种敌人或建筑第一次出现时产生短卡顿。当前没有本次实测数字，因此优先级低于前两项。

**建议改法：**利用现有开局过渡做统一预热，并按资源缓存不变的尺寸校准结果；保留首次使用时的兜底路径。先测收益，再决定是否需要对象池，不建议直接上复杂池化。

### P2-5 主入口职责过多，后续修改容易互相碰到

**收益：中；修改成本：只抽相机为中，大拆为高。**

`game/app/main.gd` 当前有 99 个函数，混合了启动、存档、肉鸽、教学、输入、相机、建造、撤销和每帧循环。它确实偏向“上帝脚本”，但不适合为了整洁一次性大拆。

**建议改法：**只沿用现有 CAMERA-MAP 文档已经界定的 `camera_control` 抽离：把相机输入映射独立出去，`view_core` 继续只管相机计算，建造与 UI 归属暂不移动。其他拆分等确有变更需求时再小步进行。

## 4. 不建议做的“优化”

1. **不把模拟数值盲目搬到 JSON。** `sim/sim.gd` 已经是集中数值表；外置配置会增加确定性、存档和黄金指纹风险，收益不明显。
2. **不为了复用而新增全局单例。** 当前多数模块已有清楚归属，只有真正跨场景且拥有全局状态的职责才值得考虑。
3. **不直接全面对象池化。** 死亡动画、闪白和模型状态都需要完整重置，先做预热与校准缓存更简单。
4. **不把遮挡剔除、光照烘焙当首选。** 当前地图是开放俯视场景，且地形可改；应先解决已确认的全量重建和每帧重复计算。
5. **不改黄金基线、探针阈值或公开接口来换取通过。**

## 5. 建议执行顺序

### 第 0 步：先把基线修到可信

1. 修模拟层无矿空目标，跑单测与黄金指纹。
2. 修视图层首次工人同步，跑场景与同步探针。
3. 给测试命令增加 `SCRIPT ERROR` 拦截，再重跑上述检查，确认是真绿。
4. 每一步单独修改、单独验收，不与其他优化混合。

### 第 1 步：阶段二，做小范围架构整理

- 只执行相机操作层抽离，保持行为与接口不变。
- 数值继续以 `sim/sim.gd` 等现有集中位置为准，不做大规模配置搬迁。

### 第 2 步：阶段三，按实测处理性能

1. 记录挖填、落墙、大波次、首次刷怪和首次建造的帧时间。
2. 优先局部地形重建，再优化实体同步，最后处理资源预热与校准缓存。
3. 每一步都保留前后耗时和完整测试结果。

### 第 3 步：阶段四，再评体验

在稳定与性能基线修好后，再逐项检查反馈、防误触、引导和设置，不在本阶段凭空列改造清单。
